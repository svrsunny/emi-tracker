# Security and privacy review

This page lists what is checked before each release, the security properties of the apps, and their
known limitations. Re-run the checks in [Repeating the review](#repeating-the-review) before every
release.

## Repository checks

| Area | Method | Current result |
| --- | --- | --- |
| Published files | `git ls-files` | Source, build configuration, tests, synthetic fixtures, demo data, documentation, screenshots, fonts and the app icon only |
| Secrets | Search for private-key headers, GitHub / AWS / Google / Slack / OpenAI token formats and `password=` literals | None. `android/app/build.gradle.kts` only *reads* signing values from a git-ignored `keystore.properties` |
| Signing material | `*.jks`, `*.keystore`, `keystore.properties` | None in the repository; all git-ignored (`android/keystore.properties.example` holds placeholders) |
| Personal data | Search for names, phone numbers, email addresses, account and loan numbers | None |
| Local paths | Search for `C:\Users`, `AppData` and drive-letter paths | None outside documentation of the standard `%APPDATA%\EMI Tracker` location |
| Network addresses | Search for private IPv4 ranges | Only documentation examples and test inputs (for example `192.168.1.50`, `10.0.2.2`) |
| Databases, backups, sync files, exports, recordings | File-type review | None outside `fixtures/`; all git-ignored |
| Test fixtures (`fixtures/`) | Field review | Synthetic only ("Fixture home", "Fixture friend", "Fixture PC") |
| Demo data (`demo/`) | Generated by `npm run demo:data` from code | Fictional names and lenders; device id `demo-device` |
| Screenshots (`assets/screenshots/`) | Image review | Taken from the real apps with the demo data; the PC's address and folder paths are masked; Android status bar in demo mode |
| Build outputs | `desktop/release/`, `desktop/dist/`, `android/**/build/` | Git-ignored; no binaries are published |
| Commit identity | `git log --format='%an %ae'` | GitHub username and `users.noreply.github.com` address |

## Security properties verified in code

- **No internet use (Windows).** `desktop/src/main/main.ts` blocks and counts every outbound
  request from the app window (`session.webRequest`); the production CSP sets `connect-src 'none'`
  (`desktop/vite.config.ts`). The end-to-end suite asserts no `http(s)`/`ws(s)` request is made.
- **No internet use (Android).** The only network client is `android/app/.../io/LanSync.kt`; it
  refuses any address that is not a home-network address (`Lan.isLocalNetwork`).
- **Wi-Fi sync encryption.** Pairing uses ECDH P-256 with HKDF-SHA256 salted by the 6-digit code;
  both sides prove the key with HMAC (`desktop/src/main/lanProtocol.ts`, `android/core/.../Lan.kt`).
  Every snapshot is AES-256-GCM encrypted with associated data binding device and direction. Shared
  test vectors (`fixtures/lan-vector*.json`) prove both implementations agree; tests check that a wrong
  code and a wrong key are refused.
- **Backups.** Optional AES-256-GCM encryption with a PBKDF2-HMAC-SHA256 key (210,000 iterations);
  passphrases are never stored.
- **App lock.** PIN / password stored only as a salted hash (scrypt on Windows, PBKDF2 on Android),
  with throttling after 5 wrong attempts.

## Known limitations

1. **Wi-Fi sync runs over plain HTTP on the local network.** The payload is encrypted and
   authenticated, but request metadata is visible on the network: device ids in the request body,
   the port, and the unauthenticated `GET /emi-sync/hello` reply (app name, protocol version and a
   "sync requested" flag).
2. **Pairing relies on a 6-digit code.** Someone actively intercepting traffic on the same Wi-Fi
   during the 5-minute pairing window could attempt to brute-force it (the PC stops accepting after
   5 wrong attempts). Pair on a trusted home network.
3. **No forward secrecy after pairing.** The pairing key is long-lived until you unpair; anyone who
   obtains it can decrypt recorded traffic. It is protected at rest by Windows DPAPI and the Android
   Keystore.
4. **Captured sync requests can be replayed** on the same network. Replaying merges data that was
   already merged, so the effect is limited to a repeated merge.
5. **The app lock is not storage encryption.** The databases are not encrypted by the app; Windows
   account security and Android device encryption protect them at rest.
6. **Unencrypted backups and exports are plain files.** Keep them private or use encrypted backups.
7. **The Windows installer is not code-signed.** SmartScreen warns on first install. Android release
   APKs are signed with the project's release key; verify downloads with `SHA256SUMS.txt`.

## Recommended repository settings

- Turn on GitHub secret scanning and push protection, and private vulnerability reporting
  (*Settings → Code security*), when the repository is public.
- Keep the Android release keystore (`android/emi-release.jks`) and its password out of the repository
  and backed up; losing them makes in-place updates of the released app impossible.

## Repeating the review

Run from the repository root before each release:

```bash
# 1. what is published (must not list databases, backups, recordings or keystores)
git ls-files
git ls-files --others --exclude-standard

# 2. secrets
git grep -nIE "BEGIN (RSA|EC|OPENSSH|PRIVATE)|gh[pousr]_[A-Za-z0-9]{20,}|AKIA[0-9A-Z]{16}|AIza[0-9A-Za-z_-]{30,}|password *[:=] *['\"][^'\"]{4,}"

# 3. home-network addresses, emails and local paths (review every hit)
git grep -nIoE "\b(10|192\.168|172\.(1[6-9]|2[0-9]|3[01]))\.[0-9]{1,3}\.[0-9]{1,3}"
git grep -nIoE "[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}" -- ':!desktop/package-lock.json'
git grep -nIE "[A-Za-z]:\\\\Users|AppData\\\\"
```

Also search for your own name, phone number, account numbers and lender names, and look at every new
image before committing it.
